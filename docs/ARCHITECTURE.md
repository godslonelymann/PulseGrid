# Architecture and guarantees

Browser requests use one origin. Next.js rewrites `/api/v1` to the local API during development. In deployment Caddy accepts traffic at the public domain/IP and proxies `/api/*` to `127.0.0.1:8000` and other requests to `127.0.0.1:3000`. The native API, worker and standalone frontend run as separate non-root Linux services. PostgreSQL and Redis bind to loopback or a private authenticated network. Only Caddy accepts public browser traffic.

FastAPI is the authority for authentication and ownership. UUID resources resolve through their owner and return the same 404 for unknown and foreign resources. Password accounts use an operator bootstrap command; account recovery requires server operator access. Optional Google sign-up creates accounts when GOOGLE_CLIENT_ID and GOOGLE_CLIENT_SECRET are configured. The authorization-code flow uses PKCE, a one-time Redis state bound to an HttpOnly browser cookie, and an ID-token nonce. Google ID-token signatures, issuer, audience, expiry and verified email are checked before a session is issued. Google subjects identify accounts; matching email addresses never silently link existing password accounts. Google-only users manage password and two-step verification at Google. Passwords use Argon2id (64 MiB, 3 iterations, 2 lanes), offloaded from the event loop with four verification slots. Redis enforces source/account/challenge limits, MFA challenge consumption and fast replay rejection. PostgreSQL additionally fences the last accepted TOTP time step so Redis loss cannot reenable a used code. Enrolled TOTP secrets and notification destinations use Fernet authenticated encryption. Recovery codes are random 128-bit values stored as SHA-256 digests and consumed with an atomic conditional UPDATE.

Access JWTs expire in five minutes by default and are checked against the live PostgreSQL session on every request. Refresh tokens are random values stored only by digest. A session row lock serializes rotation; reuse revokes the session, including all issued access tokens. Strict reuse means a lost successful response can require signing in again. Browser tabs coordinate through Web Locks and recheck access after acquiring the lock. Browsers without Web Locks do not have this cross-tab guarantee. Session cookies are host-only, HttpOnly (except the CSRF token), SameSite=Strict, and Secure in production. The separate Google state cookie uses SameSite=Lax, a ten-minute lifetime, and the Google auth path so it can accompany the cross-site callback. Mutations require a matching double-submit token and exact configured Origin. No browser local storage holds credentials. Invalid input responses remove supplied values. Security changes and factor-based session issuance serialize on the user row; challenges record the credential version so password/MFA changes invalidate earlier challenges.

The default Uvicorn command ignores forwarded headers. Client-supplied forwarding headers cannot spoof login rate limits. Behind Caddy, source limits therefore conservatively share Caddy's address; account/challenge limits remain independent. Enable trusted proxy handling only for an explicitly controlled proxy network if per-source fairness is needed. Do not use an unrestricted forwarded-header setting on a publicly reachable API.

The worker has separate scheduling, notification, and retention loops. PostgreSQL leases are claimed with `FOR UPDATE SKIP LOCKED`; only available execution slots are claimed. There are 20 global slots and two slots per hostname/port. The 60-second lease is renewed every 20 seconds, including time waiting on per-target slots. Commit locks monitor and runtime in that order and requires a live matching lease and unchanged configuration version. Pauses/edits fence earlier work. Archiving preserves settings/check history and stops checks. Explicit permanent deletion removes monitor history; queued alert payloads survive incident deletion. A killed worker's work becomes eligible after lease expiry. Connection pools use checkout validation, bounded sizes, connection/statement/lock timeouts, and no nested Psycopg pool.

Schedules advance from the scheduled timestamp and skip elapsed slots, rather than catch up in a burst. Health uses two failures for DOWN and two successes to recover a DOWN incident. A single failure is SUSPECT. A gap beyond `2 × interval + timeout` resets consecutive samples; an open incident persists across gaps/pauses and needs two fresh successes. UNKNOWN and PAUSED are display conditions, never inferred target failures or recoveries.

Results, runtime state, incident transitions and notification intents commit together. A unique `(monitor_id, scheduled_for)` and one-open-incident index prevent duplicates; `(incident_id, event_kind, channel_id)` deduplicates notification intents. Dispatchers claim an outbox row for 60 seconds, send outside transactions under a 20-second overall deadline, then record the result with lease fencing. Exponential backoff plus jitter retries eight times; exhausted work stays visible for manual retry. Notification processing does not gate probes. Delivery is **at least once**, including a possible duplicate after provider acceptance followed by a crash. Webhooks carry a stable event ID and Idempotency-Key. SMTP uses a stable Message-ID, which is not a guarantee of receiver deduplication. Disabled destinations retain pending work until reenabled. Deleting a channel deletes its delivery history; explicitly purging a monitor deletes its monitoring history; archiving preserves it.

Destination validation runs both at configuration time and at connection time. Every DNS answer must be public unless an operator explicitly allows the exact hostname/port. The HTTPX/httpcore network backend connects to a validated numeric address while preserving the original HTTP Host/TLS hostname. Cloud platform destinations such as Azure’s platform virtual IP and IPv6 transition/NAT64 mechanisms are denied even if classified globally routable. Redirects, environment proxies, embedded credentials, URL fragments, and Unix sockets are disabled. The probe currently chooses the first validated DNS address; it does not implement multi-address failover. TLS verification is on. DNS has a three-second bound; an overall deadline includes all request work. Probes return after headers and read **zero response body bytes**, so large/slow bodies cannot exhaust the worker through body reads. Webhooks use the same transport. SMTP uses an operator-configured provider, not a browser-selected host. The transport intentionally depends on pinned HTTPX/httpcore internals: rerun destination/TLS tests whenever updating them.

Metrics use UTC storage and user-local display. Check-based uptime is successful completed checks / completed checks, including every failure even before an incident opens. Coverage uses completed / floor(sum(active seconds / historical interval)), capped at 100% for fractional window boundaries and initial jitter. Missing checks are separate. Selected windows are clipped to configured raw retention, with a UI notice; purged history is excluded from the denominator. Last-check timestamps are read from retained results when configuration changes reset consecutive-sample state. Latency is time to response headers, with median/p95/p99 and histogram over successful timed checks; failures have a separate count. The latency line chart shows the current paginated results; the histogram and percentiles cover the full selected window. Raw results are retained 30 days by default, with 1,000-row deletions per minute; closed incidents and audit events have separate retention.

References used to check implementation choices: [SQLAlchemy connection pooling](https://docs.sqlalchemy.org/en/20/core/pooling.html), [Psycopg async dialect](https://docs.sqlalchemy.org/en/20/dialects/postgresql.html#module-sqlalchemy.dialects.postgresql.psycopg), [HTTPX transports](https://www.python-httpx.org/advanced/transports/), [OWASP SSRF guidance](https://cheatsheetseries.owasp.org/cheatsheets/Server_Side_Request_Forgery_Prevention_Cheat_Sheet.html).

The interface calls monitors “services” and presents one flat list. Monitors belong directly to a user; there are no bucket or group-rule tables or APIs. Enabled destinations cover all current and future monitors owned by the destination owner. Email recipients are always the owner's registered account email; client-supplied email destinations are ignored. The worker resolves that email again at delivery. Webhook secrets remain masked.

Each configuration/activity change creates a `monitor_versions` period. Check results reference the exact version used, and a composite foreign key prevents cross-monitor version references. Legacy settings that were not recorded remain unknown instead of being reconstructed.
